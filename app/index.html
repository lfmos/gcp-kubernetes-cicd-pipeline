01

O PROJETO

ENTREGA CONTÍNUA

Do código ao cluster,
com rastreabilidade.

O projeto demonstra um fluxo de entrega moderno em que cada alteração pode passar por validação, geração de imagem Docker, publicação no Artifact Registry e atualização controlada de um workload no GKE.

A aplicação pode ser executada localmente com Docker Compose. O fluxo de cloud permanece desacoplado da demonstração local e depende da configuração do ambiente GCP, do GitLab e da identidade federada.

AUTOMAÇÃO

Fluxo de entrega

PIPELINE: BRANCH / TAG

  1. 01
    </>

    Commit

    O código é versionado e enviado para o repositório central.

    git push origin main
  2. 02

    Estrutura, scripts, manifests e controles essenciais são verificados antes das próximas etapas.

    stage: validate
  3. 03
    ▣

    A aplicação é empacotada em uma imagem baseada em NGINX não privilegiado.

    docker build
  4. 04
    ⇧

    Publish

    A imagem recebe identificação pelo commit e pode ser publicada no Artifact Registry.

    $CI_COMMIT_SHORT_SHA
  5. 05
    K8s

    Deploy

    Na branch padrão, o pipeline está configurado para aplicar os manifests declarativos ao cluster GKE.

    kubectl apply
  6. 06
    ◎

    Verify

    Após o deploy, o pipeline acompanha o rollout do Deployment e verifica a disponibilidade do workload.

    rollout status

SEC.01

Autenticação sem chave fixa

O pipeline foi projetado para utilizar Workload Identity Federation e credenciais temporárias em vez de uma chave de serviço estática.

OPS.02

Health checks

Readiness e liveness probes permitem que o Kubernetes diferencie containers disponíveis de instâncias que ainda não estão prontas ou precisam ser reiniciadas.

SRE.03

Resiliência e escala

RollingUpdate, requests e limits, HPA e PodDisruptionBudget aplicam ao laboratório práticas comuns de disponibilidade e resiliência em Kubernetes.
